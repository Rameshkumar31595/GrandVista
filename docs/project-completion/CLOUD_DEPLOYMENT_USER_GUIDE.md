# GrandVista — Cloud Deployment User Guide (Render, free tier)

This guide covers the cloud deployment defined in `render.yaml`. It runs alongside the local setups (STS, the three
`docker-compose*.yml` modes) and does not change them. For the design and the verification results, see
`CLOUD_DEPLOYMENT_FINAL_REPORT.md` and `CLOUD_DEPLOYMENT_VERIFICATION.md`.

> **Cost: ₹0.** Every resource in `render.yaml` uses Render's `free` plan. Never pick a paid instance type, never add
> a payment method "to unlock" something, and never click *Upgrade*. If Render asks for a card for something in
> this guide, stop. It means a non-free option was selected.

---

## 0. What gets created

| Render resource | Type (free) | Local equivalent |
|---|---|---|
| `grandvista-web` | Static site (CDN, never sleeps) | React UI :5173 |
| `grandvista-gateway` | Docker web service | API Gateway :8080 |
| `grandvista-eureka` | Docker web service (password protected) | Eureka :9000 |
| `grandvista-auth` | Docker web service | Auth Service :8081 |
| `grandvista-room` | Docker web service | Room Service :8082 |
| `grandvista-booking` | Docker web service | Booking Service :8083 |
| `grandvista-payment` | Docker web service | Payment Service :8084 |
| `grandvista-db` | PostgreSQL (free, 1 GB, **expires 30 days after creation**) | Windows PostgreSQL :5433 |

The PostgreSQL instance holds four logical databases: `grandvista_auth_db`, `grandvista_room_db`,
`grandvista_booking_db` and `grandvista_payment_db`. Each service creates its own database on first start.
Everything in the cloud is **fresh synthetic data**. Nothing from your Windows databases is copied.

The full URLs are shown on each service's page in the Render dashboard, for example
`https://grandvista-web.onrender.com`. Render appends a random suffix if a name is already taken.

## 1. One-time deployment

**Prerequisites**

1. A free Render account, signed in with GitHub (<https://dashboard.render.com>).
2. The cloud changes are on the branch **`cloud-deployment`** of `Rameshkumar31595/GrandVista` (pushed
   2026-10-28; `main` doesn't have them yet). Pick that branch in step 2 below. **The repository is
   currently PUBLIC**, so whatever you push can be read by anyone. No secret is stored in the repository: all secrets
   are generated by Render or typed in at step 4.
3. Two values you choose now and keep somewhere private (for example a password manager):
   * **Cloud admin password**: at least 8 characters, used for `admin@cloud.grandvista.example`. Use a new
     password; never reuse a real one.
   * **Reviewer access code**: at least 12 characters, given to the reviewer. Example generator (PowerShell):
     `-join ((48..57)+(65..90)+(97..122) | Get-Random -Count 20 | % {[char]$_})`

**Steps**

1. Render dashboard → **New** → **Blueprint**.
2. Connect the GitHub repository `Rameshkumar31595/GrandVista` and pick the branch that contains `render.yaml`.
3. Render lists one database, one environment group and seven services, all marked **Free**. Check that every
   instance type says *Free*.
4. Fill in the two prompted values:
   `ADMIN_PASSWORD` (cloud admin password) and `DEMO_REVIEWER_ACCESS_CODE` (reviewer access code).
5. Click **Apply** / **Deploy Blueprint**. The first build takes about 10–20 minutes (six Maven builds plus a
   Node build). Free instances have 0.1 CPU, so each Spring service also needs 1–3 minutes to start.
6. Wait until every service shows **Live**. The four database services create their databases on first start.
   If one of them failed on its first deploy (for example, the database wasn't ready yet), open it and click
   **Manual Deploy → Deploy latest commit**.
7. Check the cross-service URLs (they come from `fromService … RENDER_EXTERNAL_URL`):
   * `grandvista-web` → Environment → `GATEWAY_PUBLIC_URL` should be the gateway's `https://…onrender.com` URL.
   * `grandvista-gateway` → Environment → `CORS_ALLOWED_ORIGINS` should be the web URL, and
     `AUTH_/ROOM_/BOOKING_/PAYMENT_PUBLIC_URL` should be those services' URLs.
   * every Java service → `EUREKA_PUBLIC_URL` should be the Eureka URL.

   If one of them is empty (Render could not resolve it on the first sync), type the URL in by hand, save, and
   redeploy that service. If you change `GATEWAY_PUBLIC_URL`, redeploy the static site: the URL is built into the
   JavaScript.

## 2. Opening the application

1. **Warm it up about 5 minutes before the review.** Free services sleep after 15 minutes without traffic. Open
   the web URL and wait; the first API call wakes the gateway, and the gateway then wakes the other services (see
   §7). You can also open each service's `/actuator/health` URL in a browser tab.
2. Open `https://<grandvista-web>.onrender.com`. If hotels don't appear yet, wait a minute and reload.

## 3. Normal login

* **Register** creates a normal guest (`ROLE_USER`) account. Use a test e-mail such as `name@example.com`.
* **Cloud administrator**: `admin@cloud.grandvista.example` with the `ADMIN_PASSWORD` from step 4. Only the
  project owner should use this account.

## 4. Demo Login for the reviewer (Ramesh, Demo Guest 2, GrandVista Manager)

1. On the login page, open the **Demo Login** tab.
2. Enter the **reviewer access code** (send it to the reviewer privately; it is not in the code or the website).
3. Click **Unlock demo accounts**. The three cards appear:
   * **Continue as Ramesh** (guest): search rooms, view dynamic prices, book, pay, cancel (refund).
   * **Continue as Demo Guest 2** (guest): a second guest; cannot see or cancel Ramesh's bookings.
   * **Continue as GrandVista Manager** (administrator): hotels, rooms, pricing rules, inventory, all bookings and
     payments, the user list.
4. The code is remembered only in that browser tab (session storage). Closing the tab forgets it.

How it is protected:

* Without the code, the demo endpoints answer **401**. No account list and no token is issued, including the
  admin token.
* After 5 wrong codes from one address, or 30 from everyone together, within 15 minutes, all attempts get
  **429** until the window passes.
* The tokens are normal signed JWTs (same expiry, 60 min) with the fixed role of each demo account. Every service
  still checks the signature and the role.
* On the cloud, the demo **GrandVista Manager cannot grant or remove administrator rights**, so nobody can turn a
  self-registered account into an administrator through the shared demo session.

**Change the access code:** `grandvista-auth` → Environment → `DEMO_REVIEWER_ACCESS_CODE` → Save. Render restarts
the service; the old code stops working immediately.

**Close demo access automatically at a fixed time:** add `DEMO_ACCESS_EXPIRES_AT` = for example
`2026-11-30T18:00:00Z` (UTC, ISO-8601). After that moment, the demo endpoints answer 403.

## 5. Disabling reviewer access

`grandvista-auth` → Environment → `DEMO_MODE_ENABLED` = `false` → Save (no rebuild). The Demo Login tab then
disappears (endpoints answer 403). Normal login keeps working. Set it back to `true` to re-enable.

## 6. Service health

| What | URL |
|---|---|
| Gateway | `https://<gateway>/actuator/health` |
| Each service | `https://<service>/actuator/health` |
| Eureka dashboard | `https://<eureka>/`, user `eureka`, password = `EUREKA_PASSWORD` from the `grandvista-shared` environment group (Render dashboard → Environment Groups) |

In the Eureka dashboard, API-GATEWAY, AUTH-SERVICE, ROOM-SERVICE, BOOKING-SERVICE and PAYMENT-SERVICE should be
**UP**. Logs: open a service in Render → **Logs**.

## 7. Sleeping services and cold starts

* A free service sleeps after 15 minutes without inbound traffic. Waking takes about 1 minute on Render's side,
  plus 1–3 minutes for Spring Boot.
* While real users are active, the gateway pings the five other services every 10 minutes. It stops 20 minutes
  after the last real request, so the whole system can sleep again and free hours aren't spent overnight.
* A sleeping service misses its Eureka heartbeats and is removed from the registry until it wakes and registers
  again (within about a minute). During that window, a request can fail with 503. Just retry.

## 8. Connecting with pgAdmin

1. Render → `grandvista-db` → **Connect** → **External** → copy host, port, database, user and password. Don't
   paste them anywhere public.
2. pgAdmin → Register → Server: Host = external host (`…singapore-postgres.render.com`), Port 5432, Maintenance
   database `grandvista_cloud`, Username/Password from Render, **SSL mode = require**.
3. The four service databases appear under *Databases*. Keep this connection separate from your local Windows
   server (port 5433) so you never run cloud SQL on the local databases.

**Optional per-service logins** (so a service can only reach its own database). Run once with psql:

```bash
psql "<EXTERNAL_DATABASE_URL>" -v ON_ERROR_STOP=1 -v auth_pw='…' -v room_pw='…' -v booking_pw='…' -v payment_pw='…' \
     -f docker/cloud/create-service-logins.sql
# tables created before this point: once per database
psql "<EXTERNAL_DATABASE_URL with /grandvista_room_db>" -v svc=gv_room -f docker/cloud/move-tables-to-service-login.sql
```

Then set `AUTH_DB_USERNAME`/`AUTH_DB_PASSWORD` (and `ROOM_…`, `BOOKING_…`, `PAYMENT_…`) on each service. The
owner login also stays on the service for the first-start database check; remove `DB_PASSWORD` there afterwards if
you want strict isolation. This needs the Render owner login to have `CREATEROLE`; if Render refuses, keep the
default setup (documented limitation).

**Backups:** free Render PostgreSQL has **no backups**. To keep a copy, run
`pg_dump "<EXTERNAL_DATABASE_URL with /grandvista_booking_db>" -Fc -f cloud-booking.backup`, repeating for each
database, and store the files outside the repository.

## 9. Redeploying after code changes

`render.yaml` uses build filters: a push that changes only `room-service/**` rebuilds only `grandvista-room`, and so
on. `docker/cloud/**` rebuilds all six Java services. To redeploy by hand: service → **Manual Deploy**. Pushing
requires the owner's own `git commit` / `git push`; nothing is pushed automatically.

## 10. Restarting or recovering a failed service

1. Open the service → **Logs** and read the first `ERROR`.
2. Typical causes:
   * `EUREKA_URL` / `EUREKA_PUBLIC_URL` empty → fix the variable (step 1.7).
   * `requires DEMO_REVIEWER_ACCESS_CODE` → demo mode is on without a code; set one or set `DEMO_MODE_ENABLED=false`.
   * Database connection refused → the database is restarting or has expired (§12).
3. **Manual Deploy → Deploy latest commit** or **Restart service**.

## 11. Monitoring free-tier usage

Render → Workspace → **Billing / Usage** shows *Free instance hours* (750 per month for the whole workspace).
All six Java services count while awake: 1 hour with everything awake uses 6 hours. Sleeping services use nothing.
If the monthly hours run out, Render suspends the free services until the next month. It does not bill you.

## 12. Database expiry

The free PostgreSQL **expires 30 days after creation**. Render then gives a 14-day grace period before deleting it.
Plan the review inside that window. To continue afterwards for ₹0, take a `pg_dump` (§8), delete the expired
database, create a new free one with the same name (`grandvista-db`) via **Blueprint → Sync**, and redeploy the four
database services. They recreate empty databases and the room service re-seeds the demo hotels.

## 13. Shutting everything down

* Pause: set `DEMO_MODE_ENABLED=false`, or **Suspend** each service (Settings → Suspend).
* Remove: delete the Blueprint's services, the static site, the environment group and `grandvista-db`
  (Settings → Delete). This doesn't touch GitHub, your local Docker volumes or your Windows PostgreSQL.

## 14. Avoiding unexpected billing

* Keep every service on **Free**. Don't enable *autoscaling*, *persistent disks*, *pre-deploy commands*,
  *private services*, *background workers* or a paid PostgreSQL plan. None of these are used here.
* Don't add a payment method. Without one, Render suspends free services when a limit is reached instead of
  charging.
* Don't "upgrade" the database when Render warns about the 30-day expiry. Follow §12.
* Check *Billing / Usage* once before the review.

## 15. Local cloud simulation (optional, no cloud needed)

```bash
bash docker/cloud/sim/run-cloud-sim.sh up      # builds the cloud images, starts them with 512 MB each
# UI http://127.0.0.1:18173  gateway http://127.0.0.1:18080  Eureka http://127.0.0.1:19000
bash docker/cloud/sim/run-cloud-sim.sh down
```

The throw-away secrets (including the simulated reviewer access code) are written to
`${TMPDIR:-/tmp}/grandvista-cloudsim.env`, outside the repository. The simulation uses its own Compose project
(`grandvista-cloudsim`), an in-memory PostgreSQL, and loopback ports only. It never touches the local stacks, the
`grandvista_pgdata` volume or the Windows PostgreSQL.
